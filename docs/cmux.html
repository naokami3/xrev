cmux 詳細解説 — エージェントの世界と cmux の世界

xrev はエージェント間の「会話」を、cmux というターミナルアプリの上に実装している。 本ページは、エージェントが見ている論理的な世界（プロンプトと応答）が、cmux の物理的な世界 （ペイン・入力欄・画面・ソケット）にどう対応し、プロンプトがどんな流れでクロスレビューを 一巡りするのかを図で解説する。対象読者は xrev の内部構造を把握したい開発者。

1. 二つの世界の対比 2. cmux のオブジェクトモデル 3. プロンプトの一生 4. うまくいかない時 5. 関連資料

1二つの世界の対比 — エージェント × cmux

エージェント（LLM）にとってクロスレビューは「相手に依頼文を送り、構造化された返事を受け取る」 会話にすぎない。しかし cmux にはエージェント間のメッセージ API は無い。あるのは ターミナルの入力欄に文字を入れる・キーを押す・画面を読むという人間向けの操作だけである。 transport.sh はこのギャップを翻訳する層で、cmux 依存はこのファイルだけに閉じ込められている。

2cmux のオブジェクトモデルと xrev が使う API

cmux（macOS・libghostty ベース）の画面は window > workspace > pane > surface の 階層でできている。xrev が相手にするのは「surface = 1 枚の端末画面」で、宛先は 呼び出し元と同一 workspace 内のタイトル一致 surface に限定する（別 workspace の同名 ペインへの誤配送を根絶するため）。制御はすべて認証付きの制御ソケット経由で行う。

3プロンプトの一生 — クロスレビュー 1 ラウンドの完全な流れ

primary エージェントの「レビューして」という 1 個のプロンプトが、cmux の上でどう相手に届き、 どう返事になって戻ってくるか。左右の注記で「エージェントから見えるもの」と「cmux 上の実体」を 対比しながら、1 ラウンドの循環を追う。

エージェント視点の要点: reviewer にとって xrev の依頼は普通のユーザー入力と区別がつかない。 だからこそ transport 層は「相手が本当に reviewer か」（プロセス証明）「全文が届いたか」（切り詰め検出） 「read-only のままか」（実 argv 検証）を送信のたびに機械検証する。

4うまくいかない時に何が起きているか

cmux の送信は間欠的に失敗する（非決定的・実測）。xrev は失敗を「異常」ではなく前提として扱い、 round_state 安全弁で総量を規制しながら再試行する。1 回の試行で成否を判定しないこと。
