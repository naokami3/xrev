# セキュリティ設計

xrev の脅威モデルを正直に記述する。**何を守り、何を守らないか**を明確にし、限界も文書化する。
過剰な安全性の主張はしない。設計の構造は [architecture.md](architecture.md)、仕様は
[`../references/protocol.md`](../references/protocol.md) を参照。

## 脅威モデル

### 守るもの

| 守るもの | 仕組み |
|---------|--------|
| 人間の最終確認 | PR は必ず `--draft`。Ready 化・マージ・確定の最終トリガは人間が引く。`finalize.sh` に非ドラフト PR を作る経路を持たせない。 |
| リポジトリを汚さない | エージェント間のやり取りに中間ファイルを使わない。ファイル生成は ADR（`docs/adr/`）のみ。 |
| 暴発防止 | `@xrev`（設定の `keyword`）や明示指示が無いときは完全に沈黙（フックは無出力）。既定の到達点は最も安全な `review`。 |
| 無限ループ防止 | 終端は機械が握る。blocker（`critical`/`high`）0 件で収束、`max_iterations`（既定 5）の安全弁付き。 |
| payload のコマンド実行**リスクの低減** | プロセス証明（`exit 17`）。reviewer ペインの tty で**前景プロセスグループ**を握るプロセスが `reviewer_process`（既定 `codex`）であることを確認し、**前景が一致しないときは Enter を送らない**。Codex 終了後に shell へ戻った端末へレビュー依頼文を送ってシェルコマンドとして実行される事故を減らす。ただし完全な防止ではない（下記「リスクと限界」参照）。 |

### 守らないもの / 前提

| 項目 | 実態 |
|------|------|
| reviewer の read-only | Codex は read-only を**前提**とするが、xrev は強制しない（権限分離は運用に委ねる）。 |
| エージェントの外部通信 | 送受信内容は cmux ソケット経由で**ローカルに留まる**（xrev 自身は外部送信しない）。ただし各エージェント（Claude / Codex）自体は各社のサービスに接続する。 |
| 秘密情報の管理 | xrev 自身は API キー等の秘密情報を**保存・要求しない**。cmux ソケットは認証付き（`CMUX_SOCKET_PASSWORD` 等がペイン内シェルに自動注入）。 |

## リスクと限界

- **reviewer 出力は信頼の上で扱う**: 契約違反（壊れた JSON・スキーマ不一致）は `parse-review.sh` が
  弾く（`invalid`）が、**指摘内容の真偽は保証しない**。誤った指摘や見落としはあり得る。
- **finalize の commit/pr は Claude のステージング判断に依存する**: 何をステージし、どんなコミット
  メッセージ・PR 本文にするかは LLM の判断であり、`finalize.sh` はそれを機械実行するだけ。
  この層に誤りがあれば不適切なコミット内容になり得る（ただし PR はドラフト止まりで人間が確認する）。
- **実行コンテキスト依存**: primary が cmux ペイン外で起動されると配管が接続できない。これは
  preflight（`exit 31`、`scripts/transport.sh ping` で確認可）で検知して停止するが、
  セキュリティ境界ではなく可用性の制約である。
- **プロセス証明は誤送信防止のヒューリスティックであり、実行バイナリの真正性は保証しない**:
  検査するのは同一 tty の前景プロセスグループと、その `comm` の basename が `reviewer_process` と
  一致することだけ。同名の別バイナリ・改竄されたバイナリは判別できない（署名検証はしない）。
  守っているのは「入力先が shell ではないこと」であって「相手が正規の Codex であること」ではない。
- **プロセス証明は「その瞬間」の観測であり、検査後のプロセス生存は保証されない**: 送信は
  「本文を1行送る → 描画待ち → Enter で確定」の多段構成で、各段の間に codex が終了する窓が残る。
  そのため検査は 3 点（早期棄却 / 本文送信直前 / **Enter 直前の最終ゲート**）で行い、Enter 直前に
  前景が変われば Enter を送らず `exit 17` で中止する。切り詰め検出（`_check_paste_intact`）は
  シェルがエコーした行でもマーカーを見つけて `ok` を返すため、この防護には使えない。
  それでも**最終検査と Enter 送出の間のごく短い競合窓は原理的に排除できない**。
- **最終ゲートで中止したペインは汚染されたものとして扱い、再利用しない**: Enter を送らなくても、
  送信済みの本文は入力行に残る。前景が shell に戻っている以上、その後の偶発的な Enter や再送で
  コマンド実行され得るため、「Enter を送らなかった」だけでは安全な終端にならない。
  残留を自動で消せるかは**表示形態に依存する**（実機確認）:
  ペーストチップ（`[Pasted Content N chars]`）は `backspace` 数回で消えるが、
  インライン表示された本文は `ctrl+u` / `ctrl+a` / `ctrl+k` / `ctrl+w` がいずれも効かず
  （反応するのは `backspace` の1文字ずつのみ）、確実な一括消去手段は未確認である。
  **中止時にどちらの形態になるかも未確認。** よって自動消去の成功を検証できない限り、
  運用要件として中止時は**ペインを閉じて reviewer を開き直す**こと。同じペインを使い回さない。
  将来 xrev に自動消去を許可してよいのは、**表示形態を機械的に識別でき、かつ消去後に入力欄が
  空であることを機械的に確認できた場合に限る**。その条件を満たせないうちは、経験上チップが
  消せる場合であっても一律に汚染扱いとし、ペインを再利用しない。
- **codex が子プロセスへ端末を譲渡している間は送信できない**: 前景プロセスグループが直下プロセスの
  どれとも一致しなくなるため、系譜を辿って緩和はせず fail closed で拒否する。安全side に倒した
  意図的な可用性の制約であり、次ラウンドで再試行すれば解消する。
- **プロセス証明は macOS / Linux の標準的な `ps`（`pid,pgid,tpgid,comm`）に依存する**: `ps` が
  無い・出力が想定形式でない環境では常に拒否される。`ps` は「一部の PID が消えていても残りを出して
  exit 0 を返す」ため、要求 PID と結果 PID の一致（欠落・余剰・重複なし）を検証したうえで判定する。
